# 注册事件回传：源码核查与补充建议

- 核查日期：2026-11-19
- 源码目录：`../web-ad/`
- 核查方式：只读静态检查，未修改业务代码、未请求真实回调、未向 Adjust 发送事件。
- 下文严格区分“源码现状”和“新增建议”；建议尚不代表已实现或已确认的业务规则。
- 已确认的业务边界：白包注册与 B 包注册是两个独立事件。保留现有白包注册链路，本次新增 B 包注册回调链路；两者不相互替代，不跨业务事件去重。

## 1. 源码能够确认的现状

## 2. B 包注册接收地址格式与生成建议（新增，待确认）

建议新增：

```text
GET <公开SDK接口基址>/v1/mmp/register_callback?app_id=<白包AppId>&package={app_name}&gaid={gps_adid}
```

- 使用部署配置中的公开 SDK 接口基址，不直接拼接后台页面的 `/web-ad` 路由；具体是否带代理前缀以该环境部署配置为准。
- 白包首次保存获得 AppId 后生成可复制模板。AppId 固定，日常编辑、修改注册事件 Key 不重新生成地址；域名随环境配置变化。
- `app_id` 为模板中固定的白包标识；多个 B 包可复制同一白包模板。
- `package`、`gaid` 延续本地已有安装/付费回调模板的字段与宏写法。`package` 必须最终得到 B 包真实包名；若 B 包 Adjust 的应用名称不是包名，应在该 B 包回调配置中填写真实包名，不能将任意显示名称当包名。宏兼容性需在开发联调中验证。
- 注册事件 Key 只用于出站注册事件，不是入站鉴权密钥，不应拼入公开接收地址充当密码。
- 若采用现有服务端全局回调鉴权配置，可在模板附带 `verify_token`；新注册入口必须实际执行校验，不能照搬当前被注释的调用。此项不新增白包表单鉴权 Key 字段，也不自动修改已有安装/付费回调。

## 3. 识别、校验与去重建议（新增，待确认）

1. 校验 `app_id`、B 包真实包名、GAID；可复用 GAID 无效值判断，并校验白包存在、B 包与该白包存在关联。
2. 按 B 包包名与 GAID 复用首次安装归因逻辑取得锁定白包，再与 URL 的白包 AppId 核对。若冲突，不向任意一方发送；保留失败原因。没有首次安装归因记录时保存为待归因，不回退到最近白包、不直接信任可修改的 URL 参数。
3. 当前应用拉活投放校验包名唯一；根据已确认的 v5 克隆规则，应用拉活副本必须填写不重复的新包名。因此本次按 B 包真实包名识别应用拉活投放，再结合 GAID 查询设备安装归因；不得以白包包名、客服投放名称或“副本”显示后缀替代 B 包真实包名。若实际历史数据存在重复包名，须先核查，不能任意取一条归属。
4. 以锁定白包的 AdjustToken、AdjustAuthToken、RegisterEventKey 出站，不接受回调方传入任意目标 Token。白包停用、配置缺失时保留原因，不发出事件；注册 Key 为空仍允许保存白包。
5. B 包注册应有独立的接收、去重及发送记录，不读取白包新设备注册记录来判重。建议按明确的 B 包注册业务事件标识去重；若采用“B 包包名 + GAID + B 包注册事件类型”的首次注册口径，应与开发确认，不能按“白包 + GAID 的任意注册”统一去重，也不能让不同 B 包的注册相互拦截。使用持久化唯一标识和原子处理防止并发重复，不能只复制安装回调的先查后插。
6. 同一 B 包注册回调命中该链路自身的成功记录时不再次发送；失败记录只能进入同一发送任务的重试流程，不能创建第二条独立任务。该判断不影响白包注册链路。

## 4. 失败、重试与结果反馈建议（新增，待确认）

本节仅针对新增的 B 包注册回调链路，不改变现有白包新设备注册的触发及处理方式。

- 先持久化接收记录和待发送任务，再反馈“已接收”；记录未持久化时返回失败，不假报接收成功。
- 后台异步发送；建议沿用现有发送的 10 秒超时，临时网络错误、超时、429、5xx 允许重试；明确的参数或鉴权错误停止自动重试并记录原因。
- 可参考机器人上报模块的 5 秒、30 秒、5 分钟三次失败重试间隔，加上首次共四次；这只是同项目已有模式，当前未接入注册到 Adjust 的发送链路。[参考](../web-ad/pkg/csbot/report.go)
- 成功、失败、待发送、待归因、配置缺失分别留痕，保留目标白包、B 包来源、GAID、发送次数和最后错误，供服务端排查；本次不据此新增后台日志页面。
- 对外可继续使用 `code/msg/data` 结构，但必须区分“已接收”“重复事件”和实际处理失败；新入口应明确真实 HTTP 状态语义，不能机械复用现有全部 HTTP 200 的包装器。
- 对外已接收后，Adjust 发送失败由内部任务重试；不能把“已接收”表述成“Adjust 上报成功”。
- 网络超时可能发生在 Adjust 实际已处理之后。跨系统的重试防重不能只依赖本地成功标记；需在接口联调中确认接收端支持的幂等机制，否则不能承诺恰好发送一次。

## 5. 已确认的业务边界

- 白包注册：沿用当前白包新设备入库后的注册上报，保留现有逻辑。
- B 包注册：B 包发生注册事件后，由其 Adjust 回调中台的新接收入口，再按本次需求处理归因与回传。
- 两类事件分别触发、分别记录和处理。即使同一设备已发生白包注册，也不构成拦截其 B 包注册的理由；反之亦然。
- 本次不取消白包注册，不用 B 包注册替换白包注册，不把两者合并为同一个业务事件或共用判重记录。

此前将两类事件视为替代关系的建议已撤回。B 包注册的具体幂等标识及新增技术建议仍需独立确认，不从白包注册触发逻辑推导。
